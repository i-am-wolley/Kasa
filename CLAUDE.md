# Kasa — session memory

Kasa is a household operating system — a model of a house that tracks what depletes (Stock), what recurs (Cycles/Routines), and what ages (Assets), and warns before anything fails. Sibling app to Miso (kitchen, `../Kitchen/Pantry-OS-App`), sharing the Nature Distilled design language but a separate deployment. Full product spec: `Base Resources/KASA_BUILD_MEMO.md` (737 lines — read it, don't guess from this summary). **This file is build-state truth; the memo is product truth.** Build plan: `C:\Users\Vinod\.claude\plans\foamy-kindling-scone.md`.

## Round 16 — icon/sizing/navigation polish, load-smoothing bug fix, People & Household deepened (added 2026-08-05, same session)

User follow-up: Today's stat tiles were visibly different heights ("Completed this week" wrapped to 2 lines); routine row icons didn't make sense (a water-tank-cleaning routine showing Utility's washing-machine-like room icon); a freshly onboarded household shouldn't open with things already due/overdue — give it a 4-day grace period; Batches cards used a generic house icon regardless of which room; load smoothing was visibly moving routines to the past and they were still showing on Today ("check if smoothing is done correctly"); the health-score breakdown rows should navigate to Today/Stock on tap; People needs a real "household" concept (code, join-anytime) and a real member-vs-help distinction (members need an email since they represent a future real account, help doesn't); the habit grid's missed color needed to be a solid box, not a border. Also: "lets initiate the firebase onboarding too tell me what I should do" — see the end of this entry.

- **Stat tile sizing** (`today.js`): "Completed this week" → "Completed" — the long label was the only one wrapping to 2 lines, and CSS grid's default row-stretch behavior meant the *other* tile sharing its row (Low stock) stretched to match, so two of the five tiles read as visibly taller than the rest. One label change fixes all five.
- **Routine icons stopped borrowing the room's icon** (`today.js`, `icons.js`): a routine row's icon was falling back to `space.icon` — reasonable-sounding until you notice Utility's room icon (a rounded box with a circle, meant to read as "utility room") looks like a washing machine, which made "Clean overhead water tank" show what looked like a washing machine glyph. Fixed with a real priority order: the linked **asset's own icon** when the routine has one (`routine.assetId` → genuinely meaningful, "Service geyser" now shows the geyser), else a new dedicated **`routine` glyph** (a recurring-cycle arrow, added to `icons.js`) — never a room icon, and never anything that could read as arbitrary for a "custom" routine either, since the fallback is always this one consistent icon.
- **4-day grace period for freshly onboarded households** (`state.js`): `seedHousehold()` now clamps every occurrence it just generated to a due date of at least 4 days out, if the engine would otherwise have it due sooner (floating routines with no completion history default to `dueAt: now` per `engine.js`'s `computeNext`, which is why a brand-new household could open with a wall of "due today"). One-time, applied right at the seeding call site — not baked into `regenerate()` itself, which every other caller (mode switches, routine edits) also uses and shouldn't be affected.
- **Batches use the real room icon** (`intel.js`, `today.js`): `spaceBatches()` now carries `spaceIcon` through to the card, replacing the hardcoded `Icon("house", ...)` — "You're already in the Bathroom" now actually shows the bath icon.
- **Load smoothing bug found and fixed** (`intel.js`) — a real one, caught live: "its moving the routines to past... i have the routines still on today." The original algorithm picked whichever *adjacent* week (before OR after the overloaded one) had more headroom, which could and did shift an occurrence's due date into a week that had **already passed** — instantly making it overdue instead of relieving anything, and it never excluded already-overdue occurrences from being "smoothed" in the first place (which never made sense — an overdue item needs doing, not deferring). Both fixed: `applyLoadSmoothing` now only considers occurrences that are still pending/due (checked via the engine's own `stateOf`, not the stored `occ.state`, which per `engine.js`'s own comment is rarely kept in sync with due/overdue), and a chosen candidate only ever shifts **+7 days forward**, never backward. Verified directly: re-ran onboarding and confirmed every generated occurrence's due date lands cleanly at the 4-day grace floor or later, with smoothed ones correctly pushed a further 7 days out — nothing in the past, nothing still showing on Today.
- **Score breakdown rows navigate** (`insights.js`): "Overdue routines" jumps to the Today tab, "Stock running low" jumps to Stock — reuses the same `document.querySelector('[data-tab="..."]').click()` pattern already used elsewhere rather than a new cross-module navigation function. "Asset service overdue" stays non-interactive (no primary tab it maps to).
- **People & Household** (`js/routes/people.js`, renamed from "People" everywhere it's referenced) — a real restructuring, not just a rename:
  - A new **Household** section at the top: the household's name and 6-char code, plus a **"Join different"** button opening the same honest join-stub sheet welcome.js uses (needs Firestore, Phase 4) — reachable anytime now, not just on first launch, per the user's explicit ask ("make it people and household where I can onboard to a household anytime").
  - The roster is now genuinely split into **Members** and **Help** sections instead of one flat list.
  - **Members now require an email** on save ("they should have an account and onboarded to the household... without email means...") — help never does, added by a member rather than having its own account. `addPerson`/`updatePerson` gained an `email` field; the two seeded mock members got plausible emails so their profiles don't open to a blank required field.
- **Welcome gate gained a Skip option** (`welcome.js`, `boot.js`) — a third path on the household step, alongside Join and Create: "Skip — start with a household of your own for now" lands straight in the app on whatever household this device already has (state.js already generates a fresh 6-char code at every boot, so Skip already means "a household of your own," not a shared fallback). Matches the user's description ("creates a household for yourself automatically") — the "which if you join another household gets removed" half isn't implementable yet without a real backend to actually replace anything into, flagged below.
- **Habit grid missed color: solid fill, not border** (`app.css`) — `.habit-cell.missed` changed from `background: var(--danger-soft)` + an inset border to a plain solid `background: var(--danger)`, matching how `.done` is also a solid fill so the two "something happened" states read the same way at a glance.
- **Verification note, not a code bug**: mid-session, the routine-icon fix appeared completely broken (blank icons) after what looked like a correct edit and a page reload. Root cause was the browser's own native HTTP cache, a layer distinct from the Service Worker's Cache Storage (already fixed in Round 14) — a plain `navigate` (or even unregistering the SW and clearing its caches) doesn't bypass it, only an actual hard-reload (`Ctrl+Shift+R`) does. Worth remembering for any future verification pass in this session: always hard-reload, not just navigate, after a JS edit.
- Verified live end-to-end: all 5 stat tiles now visibly the same height; every currently-overdue routine's icon confirmed showing the new recurring-cycle glyph (none tied to an asset in the current mock data, so all hit the fallback — a good stress test of the "never arbitrary" fallback path); Batches cards showing Bathroom/Living room's real icons; "Overdue routines" click confirmed landing on Today; People & Household's join-stub, Members/Help split, and the email-required validation (including its exact toast message) all confirmed; a fresh-browser welcome→Skip run confirmed landing directly in the working app with tab bar restored; habit grid's missed cells now a clearly solid red. Zero console errors throughout.

## Known limitations to revisit, not bugs

- `items.status`/`projectedOutAt` are static mock values, not computed — real burn-rate learning (memo §5.2) is Phase 5.
- No batching (§5.6), load smoothing (§5.7), or seasonal city map (§5.8) yet — seasonal routines just fire at raw month-window start.
- Long-press-to-reassign (memo §8.2) is not implemented — intentionally deferred rather than stubbed with a fake action.
- Deletes (space/item/asset/person/routine) use a native `confirm()` and are immediate/permanent — memo §4.4's 30-day soft-delete + "Recently removed" recovery isn't built (that's a Settings/More feature, later phase). `confirm()` satisfies §8.3's "no modal blocks anything except destructive confirmation" for now.
- `routine.js`'s condition trigger UI only supports "when this item runs out" (`op: eq, value: "out"`) — matches the only case `engine.js` needs today; extend both together if a pack needs a richer condition.
- `.tabbar` must stay nested **inside** `.app-body` in `index.html` — briefly wasn't, which silently broke the layout. No longer breakpoint-dependent since the sidebar was dropped (see locked decisions), but keep it nested regardless.
- Catalog entry `name` strings must exactly match mock-data/pack JSON names for the linkage to resolve (see the Geyser bug above) — nothing enforces this automatically. If a future pack or mock fixture references a catalog asset/item by name, double-check the exact string against `js/catalog.js` rather than assuming it'll match.
- Routine-consumes-item decrements are a flat 1 unit regardless of item unit (piece/ml/kg) and aren't restored by the 5s undo — only the occurrence/ledger snapshot is. Fine for "piece"-like consumables (toilet cleaner, detergent scoop), less meaningful for something like a 500ml handwash bottle.
- `roomTemplates.js`'s pack-derived suggestions depend on `loadPacks()` having resolved (`boot.js` fires it at startup, cached via `packs.js`'s `getCachedPacks()`). In practice this is near-instant for 5 small local JSON files, but if someone opened "Add space" in the first few milliseconds after page load, pack-covered types (bath/bedroom/living/utility/entry/whole_home) could show fewer suggestions than usual. Not defended against — low enough risk to leave as-is for now.
- Catalog custom entries (`js/catalog.js`'s `custom` array) live only for the tab's lifetime — reload and they're gone, so a freshly-typed "Shoe polish" won't survive a page refresh yet. Needs Firestore in Phase 4.
- After adding any new route file, **grep `boot.js` to confirm it's actually mounted** — `assets.js` sat fully built and completely unreachable for an entire phase before this was caught. Don't trust "the file exists and looks right" as done. (Both `wishlist.js` and `insights.js` were confirmed reachable and tested live before being called done this round.)
- Wishlist has no photo/attachment field — memo doesn't call for one and it wasn't asked for, but "what to look for" living only in the free-text Notes field is a real limitation if this grows.
- Habits can't be backfilled — `toggleHabitToday()` only ever touches today, by design (matches the "no gaming the system" spirit already applied to routine completion), but there's genuinely no way to log "I did this yesterday but forgot to check it" after the fact. Revisit if that turns out to matter more than the anti-gaming principle.
- Insights' health-score weights (`TIER_PENALTY`, the 40/30/30 caps in `computeHealth()`) are hand-picked constants for a reasonable-looking first score, not a calibrated/learned formula — same "placeholder scale, not memo §5.5" caveat the old House Line weighting had.
- "Help on leave" only surfaces the conflict (which routines fall due during a helper's leave) — it doesn't suggest or perform a reassignment. Memo §6.3 frames this as the hero feature; an actual reassign-to-X action is a reasonable next step once there's a good UI spot for it.
- Wishlist/Habits are exactly as session-only as everything else pre-Firebase (Phase 4) — nothing new here, just flagging since they're brand new collections this round.
- Wishlist checklist sub-items can't be renamed/re-kinded once added — only toggled done or deleted. Fine for the "quick checklist" use case this was built for; revisit if projects turn out to need heavier editing.
- A "weekly_count" habit (e.g. "gym 3x/week") is due on *any* day until that week's quota is hit, with no specific day it nags harder on — matches how such goals are usually thought about ("3 times this week," not "Mon/Wed/Fri specifically"), but means it could show up as due every remaining day of the week if left alone, not just once.
- Habit "Custom days" frequency stores `days` as JS `Date.getDay()` numbers (0=Sun..6=Sat) — chip values round-trip as strings through the DOM (`readChipGroup`), converted back to numbers at save time in `buildHabitFrequency()`. If this data model is touched again, keep that numbering convention rather than switching to ISO's Mon=1 without updating both `routine.js` and `state.js`'s `isHabitDueToday`.
- Tasks have no recurrence, effort, or consequence tier by design (that's what separates them from Routines) — a task that should repeat has to be manually re-added after completion. If recurring one-off reminders turn out to be a real need, that's a genuinely new shape, not a small extension of the current Task model.
- The member filter on Today doesn't extend to Wishlist or Insights — it was asked for and built specifically for Today's Overdue/Due lists. Revisit if per-person filtering turns out to matter on those other screens too.
- `.named`'s Fraunces-italic styling was removed per explicit dislike, but the font import and class name remain — a future "special occasion" surface could reuse both without re-plumbing, but until then `.named` is just semibold, so the name reads as more ceremonial than it currently is.
- Undoing a wishlist checklist sub-item never deletes the real Stock/Assets record an asset/item "Buy" already created — only the checklist's own done flag reverts. Re-clicking "Buy" after an undo would create a second real record rather than reusing the first. Acceptable for the "oops, wrong tap" case this was built for; revisit if it turns out people undo-then-rebuy on purpose.
- Today's "This week" view buckets by raw due-date offset, independent of each routine's own trigger window — this means a routine can appear in "This week" a few days before it would ever show up in the plain "Today" view (by design, see Round 13), so the two views' row counts for the same date range won't always match the engine's own due/pending state one-for-one. That's intentional, not a bug.
- Load balancing (§5.5) computes a single rolling-30-day snapshot, not the memo's literal "persists for 2 consecutive weeks before surfacing" — there's no cross-session weekly-aggregate storage pre-Firebase to check persistence against. Revisit once Phase 4 gives it somewhere to remember last week's number.
- Consumable coupling (§5.9) is informational only, and doesn't model the memo's literal "RO membrane" example — the catalog has "RO filter cartridge," not a separately-tracked membrane — so the signal is "a water-treatment asset was serviced recently, here's what's nearby that might need attention," not a precise per-part coupling.
- Seasonal intelligence (§5.8) only has a real season map for Bengaluru, matching the only city the memo itself specifies data for. Any other household's `city` value gets no seasonal card at all rather than a guessed map.
- The snooze-learning day-of-week signal (§5.4) needs real history for a specific routine to have both several logged snoozes *and* several ledger completions — genuinely thin for a fresh household. The seeded demo (`mock-data/snoozeLog.js` + one ledger entry) is close but not perfectly reliable at demonstrating it, since one of the two hardcoded historical completion dates happens to land on a weekday and dilutes the pattern — the underlying detection logic is correct (verified directly), just don't expect the mock data alone to visibly trigger it on every load.
- Load smoothing (§5.7) runs once per occurrence lifecycle (the `occ.smoothed` guard) and nothing currently un-sets that flag — an occurrence that gets snoozed-then-woken-then-regenerated fresh after actual completion starts unsmoothed again as expected, but there's no path back to "eligible to smooth again" for the same still-open occurrence if the household's effort ceiling changes mid-week. Low-risk for a single-session mock app; revisit if this becomes a real multi-week persisted household.
- The service worker (`sw.js`) is network-first for a deliberate reason (see Round 14) — don't change it back to cache-first without re-reading why, since that exact choice silently broke live verification once already.
- The welcome gate's `kasa_intro_done` localStorage flag is not a real "already onboarded" check — it's "has this browser seen the intro." Combined with state being in-memory-only pre-Firebase, a returning browser skips straight to the app but with the household reset to the original mock demo, not whatever was actually created last time. Once Phase 4 lands, this flag should be replaced with a real auth/household check.
- "Join a household" on the welcome screen is a real input with a stub action — it always explains that joining needs Firebase and points at "Create a new one" instead, regardless of what code is typed. Nothing validates the code's shape beyond 6 chars/uppercase; there's no backend yet to validate against.
- The Utility-mandatory guard (`deleteSpace()`) assumes exactly one space has `type: "utility"` — `requiresItemsFieldHtml()`'s `state.spaces.find(s => s.type === "utility")` picks whichever one it finds first if a household somehow ends up with more than one (nothing currently prevents *adding* a second Utility-type space, only deleting the existing one). Low-risk edge case, not defended against.
- The household `code` generated by `generateHouseholdCode()` isn't looked up or validated anywhere — it's purely displayed (toast + More sheet) so the shape of the real Miso-style `households/{code}` pattern exists before Phase 4's Firestore backend makes it actually functional.
- Welcome's "Skip" household option isn't actually distinguishable from any other household this device might have — it just lands on whatever's already in `state` (the mock demo, freshly coded). The user's own description ("which if you join another household gets removed") implies a real join should later *replace* a skip-created household rather than coexist with it; there's no way to implement "replace" meaningfully without a real backend to replace *from*, so this is deferred to Phase 4, not built as a half-measure now.
- A member's `email` field is required-on-save but not validated for actually being a valid email shape — any non-empty string passes. Real validation (and real verification) is a Phase 4 concern once sign-in is real.
- People & Household's "Join different" sheet and welcome.js's own join step are two separate, near-identical implementations of the same honest stub (not shared code) — duplicated deliberately rather than over-abstracted for two call sites that will both need to become real (and possibly diverge) once Phase 4 lands.
