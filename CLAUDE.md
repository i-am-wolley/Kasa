# Kasa — session memory

Kasa is a household operating system — a model of a house that tracks what depletes (Stock), what recurs (Cycles/Routines), and what ages (Assets), and warns before anything fails. Sibling app to Miso (kitchen, `../Kitchen/Pantry-OS-App`), sharing the Nature Distilled design language but a separate deployment. ## Locked decisions (confirmed with user, deviate from the memo's literal defaults)

| Decision | Why |
|---|---|
| **UI-first, mock data before Firebase** — not the memo's §12 literal order | Same pattern as sibling app Mina: visible progress every session. `mock-data/` fixtures match real entity shapes so wiring Firebase later is a data-source swap. |
| **Mobile AND tablet simultaneous first-class targets**, desktop (`>1024px`) deferred | Kasa's core interaction (swipe done/snooze while standing in a room) is phone/tablet-in-hand, unlike Mina's desktop-review app. |
| **New, separate Firebase project** (not folded into Miso's `pantry-os-prod`) | Cross-project Miso→Kasa flow possible later via a second `FirebaseApp` instance or cross-project IAM. `users/{uid}` carries `email` from day one so a future linking step has something to match on. |
| **Design tokens pulled from the real `miso-design` skill**, not memo §9.1's fallback hexes | The memo's §9.1 values are its own documented "fallback if extraction is incomplete" — extraction wasn't incomplete. |
| **Bottom tab bar at every breakpoint up to real desktop** — not memo §8.1's "sidebar on tablet+" | Tablet apps that keep bottom tabs (Instagram/X on iPad) read as more consistent and stay thumb-reachable for in-hand swipe interactions. Sidebar deferred to the true desktop pass. |
| **Type is Geist + Geist Mono + Fraunces italic**, not Playfair+Karla | Real Miso ships Geist/Geist Mono; Fraunces italic was reserved for "named things" (routine titles, asset names) but later dropped to plain semibold, see Round 12. |
| **5th tab is Wishlist, not More** | "More" (Assets/People/onboarding) moved to a header button next to the logo, freeing the 5th tab for Wishlist. Still exactly 5 tabs (memo's own limit). |
| **Habits are personal, separate from Routines** — new concept, not in the memo | Person-scoped, no space, no trigger, just a daily done/not-done log + 72-day grid. Routines stay household/space-scoped on the 6-trigger engine. Future direction: household vs. individual routine classification. |
| **Phase 5 explicitly excludes §5.2 burn-rate learning and §5.3 adaptive intervals** | Both need real longitudinal usage history a fresh household doesn't have; user's explicit call, "rest all is nice." Revisit only if asked. |
| **A household can contain more than one House** — new layer above Space | Every space carries a `houseId`; items/assets/routines inherit house scoping transitively through `spaceId`. See Round 17. |
| **Schema-version migration mechanism** (`js/migrations.js`) | General-purpose version-bump mechanism, replaces old ad-hoc per-field backfills. See Round 17 for the first real migration; it's been used for every schema change since without needing to change the mechanism itself. |
| **Google sign-in is mandatory** — no local-only/Skip path | Apple and email-link auth deliberately still not wired. See Round 18. |
| **Firestore: one `data/main` document per household**, not granular collections | A household's data is nowhere near the 1MiB ceiling; none of `state.js`'s ~30 mutators needed to change; `db.js`'s autosave piggybacks on the existing `subscribe()`/`notify()` signal. Revisit only if a household's data actually approaches the size ceiling. |
| **Onboarding creates spaces only** — no assets/stock/routines/tasks/habits | The room-by-room "suggested for this space" flow (House's own Add Space) is still how content gets added, just never automatically during the six-question wizard. See Round 18. |
| **Notifications are on-device/foreground-only**, not true background push | Real push needs FCM + a scheduled Cloud Function + the Blaze billing plan, none of which exists yet. `js/notify.js` is the honest client-only version. Revisit once Phase 6's Cloud Function proxy exists anyway. See Round 19. |
| **Real-time sync stays whole-document last-write-wins**, not field-level merge | Matches the one-`data/main`-doc decision — real per-field merge needs the granular layout that was explicitly avoided. `onSnapshot` (Round 20) makes another device's changes show up live; doesn't resolve same-moment conflicts. |

## Standing gotchas (recurring lessons, apply to future rounds)

- **After adding a new route file, grep `boot.js` to confirm it's actually mounted.** `assets.js` was fully built and completely unreachable for an entire phase before this was caught (Round-early "Global asset + item catalog" entry).
- **Catalog entry `name` strings must exactly match mock-data/pack JSON names** for `getOrCreate()`'s exact-match linkage to resolve, or content silently mints a throwaway custom entry instead of linking to the real one (bit the "Geyser" entry twice).
- **Always hard-reload (`Ctrl+Shift+R`), not just navigate, after a JS edit** — the browser's own HTTP cache (distinct from the Service Worker's Cache Storage) can serve a stale module. The Service Worker (`sw.js`) is deliberately **network-first** for JS/CSS for the same reason — don't revert to cache-first without rereading Round 14's own note on why that once silently broke live verification.
- **Date-string lookups must use the same local-time convention everywhere.** `todayStr()`/habit-log writes never normalize to local midnight; a lookup helper that did (`habitStreak`, Round 66/71) silently shifted every date one day in positive-UTC-offset zones. Match convention, don't "fix" a date by adding `setHours(0,0,0,0)`.
- **A mutator that resets/regenerates related state (occurrences, etc.) must gate on "did the relevant field actually change,"** not "does this field exist" — `updateRoutine`'s occurrence-drop-and-regenerate logic once fired on *every* edit to a never-completed routine because it checked `if (trigger?.startDate)` (true for all routines post-Round-23) instead of whether the start date itself changed. Any self-correcting/regenerating logic needs a real diff check, not a presence check.
- **Firestore is one `data/main` doc per household, whole-document last-write-wins.** A live `onSnapshot` listener can echo/clobber test data written moments earlier from a separate call — when doing disposable test-data work against a real signed-in household, create-test-verify-delete inside as few separate calls as possible.
- **`xathurak@gmail.com` is the standing disposable test account** for anything requiring real Google auth in the live app; the Chrome extension generally cannot get past Google's OAuth consent screen on its own, so most "live" verification in this project is either that real test account or a synthetic on-page DOM injection against the real stylesheet.
- **A `<label>` with no `for` attribute forwards a click anywhere inside it (including blank padding) to its first labelable descendant.** Any sheet field built as `<label class="field">` wrapping a multi-button chip-group will silently reset the selection on a stray click. `field()` now renders a plain `<div>`.
- **`overflow:hidden` clips at the padding edge, not the border edge** — a border stays fully visible and drawn at its own true edge even when a child pseudo-element is clipped by the parent's overflow.
- **A synchronous `notify()` call inside a `getState()`-triggered mutator can self-trigger a cascade** — `applyAutoDepletion()` once re-ran on every nested render because "elapsed time since last checkpoint" is always nonzero even microseconds later; needed a minimum-meaningful-elapsed-time floor (superseded by whole-day flooring in Round 26).
- Reaching real signed-in screens for verification when the extension can't complete Google OAuth: fall back to disposable synthetic DOM injection against the live stylesheet, screenshot, then remove — documented per-round as "the synthetic on-page-injection technique."
- **`occurrences` are intentionally NOT persisted to Firestore** (re-derived by `regenerate()` from routines/ledger/assets/items on every load) — correct for anything actually derivable from those, but any occurrence-level field that ISN'T derivable (snooze state, see Round 73) has to get its own small persisted mirror (`state.snoozes`), or it silently evaporates on reload. Same root cause previously bit `firstFloatingOccurrence` (Round 45/46) from the opposite direction (a field recomputing itself into the wrong answer on reload, not vanishing) — check both directions before assuming a derived-occurrence field is safe.
- **`regenerate()`'s `openRoutineIds` must count every non-`"done"` occurrence as open, snoozed included** — excluding `"snoozed"` (on the theory that only `wakeSnoozedOccurrences()` should touch it) meant ANY unrelated mutation anywhere in the app that also calls `regenerate()` would treat a still-actively-snoozed routine as occurrence-less and spawn a duplicate fresh occurrence alongside it (Round 73). `wakeSnoozedOccurrences()` already runs first and promotes any genuinely-expired snooze back to its real state, so by the time `openRoutineIds` is built, anything still `"snoozed"` is guaranteed still active — safe to count as open.

## Architecture (what's built)

- `tokens.css`, `app.css` — full design-token set + shared primitives (list-row, stepper, sheet form fields, chip-group, tile grid).
- `js/engine.js` — all six trigger types (`fixed_calendar` with a minimal RRULE subset — `FREQ=MONTHLY;BYMONTHDAY=N`/`FREQ=WEEKLY;BYDAY=XX,YY` (multi-day) only; `floating_since_last`; `usage_meter`; `condition`; `seasonal`; `on_mode`). `stateOf`/`overdueDays` compare at **day granularity**, not exact timestamps. A mandatory per-routine `startDate` (Round 23) resolves the first occurrence for every trigger type: future start date wins outright; past/today resolves per-type (floating routines walk the interval to the most recently passed grid point, calendar routines resolve the current cycle directly — both fixed in Round 45/46 after each independently had a "never-completed routine can't go overdue across a session reload" bug). An optional "Always on Saturday" (`snapToSaturday`) flag snaps a computed floating-interval date forward to the nearest Saturday without adding a needless week.
- `js/state.js` — Firestore-backed store (`serializeState`/`hydrateState`), full CRUD for houses/spaces/items/assets/people/routines/tasks/habits/wishlist, `regenerate()` re-runs the engine after any mutation that could unlock/lock occurrences, 5-second undo via a single-slot last-action snapshot (occurrence complete/snooze only). `applyAutoDepletion()` floors elapsed time to whole days before stepping quantity down (Round 26) — never a continuous fraction. `logActivity()` writes into a capped-at-500-entries `activityLog`.
- `js/migrations.js` — numbered schema-version steps (`CURRENT_SCHEMA_VERSION` + a keyed `migrations` object), applied once via `migrate(state)` right after initial state construction. Steps so far: v1→2 multi-house + `houseId` backfill, v2→3 notify settings, v3→4 smoothing mode default, v4→5 consequence-tier rename backfill, v5→6 activity log, v6→7 asset `category` backfill, v7→8 wishlist sub-item `cost:0` backfill, v8→9 `state.snoozes` backfill.
- `js/intel.js` — Phase 5 intelligence, all pure(ish) functions over `state`: snooze learning (§5.4), load balancing across members only (§5.5), same-space/same-vendor batching (§5.6), load smoothing capped at a 20-point/week ceiling, cosmetic-tier occurrences only (§5.7), Bengaluru-only seasonal keyword matching (§5.8), asset failure prediction + consumable coupling + neglect clustering (§5.9). §5.2/§5.3 deliberately excluded.
- `js/catalog.js` — master asset/item catalog (77+ asset entries, 53+ item entries), each `{key, name, icon, category, expectedLifeYears, suggestedRoutines, ...}`. `getOrCreate(name, type)` does exact-name matching; no match registers a session-scoped custom entry (`AST-CUSTOM-N`) — not persisted, a real Phase-4+ gap (see Known limitations).
- `js/roomTemplates.js` — per-space-type suggested content. Pack-covered types (bath/bedroom/living/utility/entry/whole_home) derive live from `packs/*.json`; pack-uncovered types (balcony/study/storage/outside/pooja/entertainment/dining/garage/terrace) are hand-authored.
- `js/packs.js` + `packs/*.json` (13 packs: core, bath, laundry, help, appliances, utility, bedroom, living, plants, admin, entry, vehicle, study) — `generateFromArchetype()` filters by `appliesWhen` (always/spaces/householdHelp/has), dedupes spaces by type, resolves each routine's asset reference to a real generated asset id. IDs are `genId()`-based (timestamp-salted), not a bare per-session counter — see Round 24's id-collision bug below.
- `js/routes/today.js` — stat row (Overdue/Due today/This week/Completed/Low stock), Overdue/Due Today/Habits/Shopping-list sections, member filter, Today/This-week toggle, effort/Batches/Smoothen chips, pointer-based swipe gestures (direction-disambiguated, rAF-batched — see Round 6).
- `js/routes/house.js`, `stock.js`, `assets.js`, `people.js`, `routinesTasks.js`, `houses.js`, `wishlist.js`, `insights.js`, `activity.js`, `welcome.js`, `onboard.js` — full CRUD screens per the memo, reached via the tab bar or More.
- `js/routes/routine.js` — the shared plain-language builder for Routine/Habit/Task (Kind chip-toggle, Round 11), trigger-type chip swaps param fields to match exactly what `engine.js` can execute.
- `js/boot.js` — tab shell (Today/House/Stock/Insights/Wishlist) + header More button + house picker; unbuilt screens render an honest "not built yet" placeholder.
- `js/auth.js`, `js/db.js`, `js/firebase.js` — Google sign-in (popup w/ redirect fallback), Firestore persistence + `onSnapshot` real-time sync, offline persistence via `persistentLocalCache`/`persistentMultipleTabManager`.
- `js/notify.js` — on-device notification summary, foreground/open-tab only, gated by `household.notifySettings`.
- `mock-data/` — the original hand-seeded 2BHK household, now only the pre-auth/pre-onboarding default demo.

## Changelog (condensed, newest first)

- **R73** (2026-08-17) Fixed a real bug, user report: "when i snooze a routine which is overdue, it goes out in the session, but when i reopen the app after closing it appears again as overdue." Root cause: `occurrences` is deliberately excluded from Firestore persistence (re-derived by `regenerate()` on every load), but a snoozed occurrence's `state`/`snoozedUntil` isn't derivable — it's a real user action, not something routines/ledger/assets/items can reconstruct — so a reload wiped it and the routine came back showing its natural (still-overdue) state immediately, as if the snooze had never happened. Fixed with a small persisted mirror, `state.snoozes` (`{routineId, snoozedUntil, snoozeCount}`, migration v8→9), that `regenerate()` reapplies onto a freshly-regenerated occurrence after a reload if the snooze window hasn't actually elapsed yet. Also fixed the underlying `openRoutineIds` bug this touched: excluding `"snoozed"` from "open" meant ANY unrelated mutation's `regenerate()` call (not just an immediate one from `snoozeOccurrence` itself, which was already known and deliberately avoided) could spawn a duplicate occurrence alongside a still-actively-snoozed one — now only `"done"` is excluded, verified with a Node-side simulation (snooze → reload → still hidden; snooze → unrelated mutation → no duplicate; snooze → undo → no stale `state.snoozes` record left to resurrect on the replacement occurrence). Correct snooze semantics, confirmed with user: snoozing hides the occurrence from Today for N days without changing its actual due date — once the snooze window elapses it reappears in whatever state it would honestly be in by then (still overdue if it already was, since snoozing delays visibility, not the deadline).

## Known limitations to revisit, not bugs

- `items.status`/`projectedOutAt` beyond the static burn-rate projection are not learned — real burn-rate learning (§5.2) is explicitly excluded, see Locked decisions.
- Long-press-to-reassign (memo §8.2) not implemented — deferred, not stubbed.
- Deletes use a native `confirm()` and are immediate/permanent — memo §4.4's 30-day soft-delete + "Recently removed" isn't built.
- `routine.js`'s condition trigger UI only supports "when this item runs out" — matches what `engine.js` can execute today.
- Catalog custom entries (`js/catalog.js`'s `custom` array) are session-only, not persisted to Firestore — a freshly-typed custom catalog name won't survive a reload.
- Routine-consumes-item decrements are a flat 1 unit regardless of item unit (piece/ml/kg), and aren't restored by the 5s undo (only the occurrence/ledger snapshot is).
- Insights' health-score weights (`TIER_PENALTY`, the 40/30/30 caps) are hand-picked constants, not calibrated/learned.
- "Help on leave" only surfaces the conflict, doesn't suggest or perform a reassignment.
- A "weekly_count" habit is due on *any* day until quota is hit — no specific day it nags harder on.
- Multi-house filtering doesn't reach Insights' Phase 5 intelligence sections or Wishlist — those still read/act across the whole household regardless of the header house picker. Deliberate scope boundary, revisit if multi-house households actually start relying on them.
- Undoing a wishlist checklist sub-item never deletes the real Stock/Assets record its "Buy" already created — only the checklist flag reverts.
- Load balancing (§5.5) is a single rolling-30-day snapshot, not the memo's literal "persists for 2 consecutive weeks before surfacing" — no cross-session weekly-aggregate storage to check persistence against pre-Firebase-being-load-bearing-enough.
- Consumable coupling (§5.9) is informational only and doesn't model the memo's literal RO-membrane example (catalog only tracks "RO filter cartridge").
- Seasonal intelligence (§5.8) only has a real season map for Bengaluru.
- The welcome gate's `kasa_intro_done` localStorage flag means "this browser has seen the intro," not "this browser is authenticated" — real auth/household state should replace it now that Phase 4 is done; worth confirming it actually has been superseded rather than left dangling.
- "Join a household" by code doesn't validate against anything real yet beyond shape (6 chars, uppercase).
- A member's `email` field is required-on-save but not validated as a real email shape.
- People & Household's "Join different" sheet and welcome.js's own join step are two separate, near-identical implementations (different pre-conditions — welcome.js has no existing household to tear down first).
