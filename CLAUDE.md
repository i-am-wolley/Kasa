# Kasa — session memory

Kasa is a household operating system — a model of a house that tracks what depletes (Stock), what recurs (Cycles/Routines), and what ages (Assets), and warns before anything fails. Sibling app to Miso (kitchen, `../Kitchen/Pantry-OS-App`), sharing the Nature Distilled design language but a separate deployment. Full product spec: `Base Resources/KASA_BUILD_MEMO.md` (737 lines — read it, don't guess from this summary). **This file is build-state truth; the memo is product truth.** Build plan: `C:\Users\Vinod\.claude\plans\foamy-kindling-scone.md`.

## What's actually built (Phase 0-3)

- `tokens.css`, `app.css` — full token set + shared primitives (list-row, stepper, sheet form fields, chip-group) used by every screen.
- `js/engine.js` — all six trigger types (`fixed_calendar` with a minimal RRULE subset — `FREQ=MONTHLY;BYMONTHDAY=N` and `FREQ=WEEKLY;BYDAY=XX` only, extend as real packs need richer recurrence; `floating_since_last`; `usage_meter` with velocity-based estimation; `condition` with a 1-day default cooldown; `seasonal`; `on_mode`), `stateOf`/`overdueDays` compare at **day granularity** (not exact timestamps — see comment in the file for why: condition/on_mode occurrences set `dueAt = now`, and a sub-day render delay was flickering them into "overdue by 0 days").
- `js/state.js` — in-memory store standing in for `db.js`; full CRUD for spaces/items/assets/people/routines, `regenerate()` re-runs the engine after any mutation that could unlock/lock occurrences (mode switch, routine add/edit/toggle) so mode-gated and mode-paused routines respond live; 5-second undo via a single-slot last-action snapshot (occurrence complete/snooze only, not CRUD — see limitations).
- `js/routes/today.js` — House Line (30 ticks, `-6`/`+23` day window, tick height = summed `effort × consequenceWeight`, colour = heaviest tier that day), Overdue/Due Today sections (only damaging/safety tiers render loud), effort-1 filter chip, pointer-based swipe gestures (threshold 90px).
- `js/routes/house.js` — spaces grid → space detail (routines/stock/assets for that space), add/rename/delete space with a reassign-or-delete-contents prompt (memo §4.4). Item/asset rows here are prune-only (trash icon); full edit lives in Stock/Assets.
- `js/routes/stock.js` — Out/Low/Expiring/OK sections, qty steppers, add/edit/delete item, "Build shopping list" copies out+low items to the clipboard (memo §7 routing, not ordering).
- `js/routes/assets.js` — cards sorted by next service due, warranty/service countdown copy, vendor `tel:` call link, "Mark serviced" (re-baselines `lastServicedAt`/meter so `usage_meter` routines start counting fresh), add/edit/delete.
- `js/routes/people.js` — member/help roster, add/edit/delete, add leave entries; reached via More → People (not a primary tab, per memo §8.1's 5-tab limit).
- `js/routes/routine.js` — the shared plain-language routine builder (memo §4.2), reused by House's "+ Add" and each routine row's edit; trigger-type chip swaps which param fields show, matching exactly what `engine.js` can execute (no UI for capabilities the engine doesn't have).
- `js/boot.js` — tab shell (Today/House/Stock/Insights/More) + a More menu for sub-screens; unbuilt screens render an honest "not built yet, Phase N" placeholder, never fake content.
- `mock-data/` — the original hand-seeded 2BHK household is now only the boot-time default (shown until onboarding is re-run); still useful as a stable, hand-tuned demo of all 6 trigger types with a realistic overdue/due mix.
- `packs/core.json`, `bath.json`, `laundry.json`, `help.json`, `appliances.json` — real content in memo §10's schema, priority order per the memo. `appliesWhen` supports `always`, `spaces` (matched against `impliedSpaceTypes()` — every home gets bath/bedroom/living/utility/entry/whole_home, `balcony` added only if "Balcony/garden" was picked), `householdHelp`, and `has`.
- `js/packs.js` — `loadPacks()` fetches the 5 JSON files; `generateFromArchetype(answers, packs)` filters by `appliesWhen`, dedupes spaces by type across packs, resolves each routine's `assetRef` (a pack-local asset name) to a real generated asset id. Verified live: switching "Household help" to "None" correctly drops `help.json`'s routines; all 5 packs merge into one coherent household with zero `engine.js` changes (the memo's own acceptance test).
- `js/routes/onboard.js` — six chip questions on one scrollable screen (not a multi-step wizard — matches the memo's "~40 seconds" intent without extra navigation), a generating skeleton (600ms), then a confirm screen grouped by room with a one-tap "Keep/Removed" bulk toggle per space (memo §3.1 Step 4). Confirming calls `state.seedHousehold()`, which replaces spaces/items/assets/routines and clears the ledger (fresh household, nothing done yet — everything reasonably starts "due today").
- Reachable via More → "Re-run onboarding" rather than gating app boot — there's no real "first run" concept yet without auth/persistence (Phase 4), and gating would make the hand-tuned demo household harder to get back to for continued testing.

## Global asset + item catalog (added 2026-08-03, user request)

User reported Assets couldn't be created/edited. Root cause: `assets.js` was fully built in Phase 2 but never wired into `boot.js`'s router — completely unreachable, not a logic bug. Fixed by adding it under More (same pattern as People), with a back button. **Lesson: after writing a new route file, grep `boot.js` to confirm it's actually mounted before calling the screen done** — Phase 2's own verification pass missed this because it never tried to reach Assets by anything other than House's read-only per-space list.

While fixing that, the user asked for a real catalog system: every asset/item should carry a stable key, typing a name should suggest existing catalog entries to select (never silently duplicate the same real-world thing under a new key), and each catalog entry should have its own distinct icon. Built as:

- `js/catalog.js` — master data, not household data. `ASSETS` (77 entries) and `ITEMS` (53 entries) each `{key, name, icon, category, ...defaults}`, curated across more than one climate/region on purpose (storage geysers + tankless heaters + US tank heaters; evaporative coolers + boilers + furnaces; inverters/UPS + generators + solar) — not just the Indian-apartment set the mock/packs use. `getOrCreate(name, type)` is the core primitive: exact-name match reuses the existing key, no match registers a new session-scoped custom entry (`AST-CUSTOM-N` / `ITM-CUSTOM-N`) so retyping that same name later finds it instead of minting another one. Custom entries are **session-only** (not persisted) — Phase 4 should move `custom` into Firestore as a real, growing per-household or global catalog.
- `js/ui/icons.js` — ~77 unique per-asset icons (one identity per entry, per the user's explicit ask) plus ~15 shared item-*category* icons (bath/laundry/cleaning/paper/pest/utility/electrical/fragrance/safety/garden/pet/vehicle/filters/admin/electronics-accessory — same "group by category" pattern the memo's own §9.4 icon table already uses, applied at catalog granularity since ~53 individual consumables would mostly look like indistinguishable bottles/packets at 16-18px anyway).
- `js/ui/components.js` — `catalogField`/`wireCatalogField`/`resolveCatalogField`: a name `text-input` + live suggestion dropdown (`.catalog-suggestions`). Selecting a suggestion fills the field, stamps `input.dataset.catalogKey`, and (in Stock/Assets' `onSelect` handlers, add-mode only) pre-fills unit/par-level/service-interval from the entry's defaults. Saving without selecting still resolves correctly — `resolveCatalogField` calls `getOrCreate`, which finds an exact-name match even if the user never clicked a suggestion.
- Wired into `stock.js` (add/edit item) and `assets.js` (add/edit asset) — both store `catalogKey` + `icon` on the record and show the key read-only in the edit sheet ("Catalog key: ITM-TOOTHPASTE"). `packs.js` and `state.js`'s initial mock-data load were **also** updated to resolve every pack-generated and hand-seeded item/asset through `getOrCreate`, so pre-loaded content is catalog-linked too, not just newly-created entries — this is also why `mock-data/assets.js`'s AC entry was renamed from "AC — bedroom" to "Split AC" (had to match the catalog's exact name to link correctly).
- **Round 2 (same session)**: user asked for much broader coverage (electronics, furniture, more kitchen appliances, vehicles — "look across the work across each continent and country") and for `openItemSheet`/`openAssetSheet` to be reachable with a pre-filled space directly from House's per-space detail view, not just from Stock/Assets. Catalog grew from 33/44 to 77/53 entries (added electronics & AV, furniture, more kitchen appliances, outdoor/garden equipment, vehicles, plus a few new item categories: dishwashing, more personal care, electronics accessories). `stock.js`'s `openItemSheet` and `assets.js`'s `openAssetSheet` were refactored from positional `(item)`/`(asset)` args to `({ item, defaultSpaceId })`/`({ asset, defaultSpaceId })` options objects and exported; `house.js` now imports both and wires "+ Add" buttons in the space detail's Stock/Assets sections (same pattern as the existing Routines "+ Add"), plus made item/asset rows there tap-to-edit (previously trash-only).
  - **Bug caught during this refactor**: `assets.js`'s `assetFormFields(asset, state)` helper wasn't passed `defaultSpaceId`, throwing `ReferenceError` and silently breaking the House "+ Add asset" button (sheet never opened). Fixed by threading `defaultSpaceId` through as a third argument. Caught immediately via console error checking, not left for the user to find — worth remembering that any helper function extracted from a route body needs its captured variables re-checked when the parent function's signature changes.
- Verified live: typing "clean" surfaces Toilet/All-purpose/Glass/Floor cleaner with correct distinct icons; selecting one auto-fills unit+par level; typing a brand-new name ("Shoe polish"), saving, then retyping the same name later correctly surfaces it as a suggestion instead of creating a second entry; adding an asset from House's Balcony detail correctly pre-filled Space to "Balcony" and surfaced both "Water softener" and "Sofa" for a "sof" search.

## Assets ↔ routines ↔ stock, properly linked (added 2026-08-03, same session)

User reported the Assets card's "Service due in N days" didn't update after editing the service interval, and asked "will that auto-create a routine?" — surfaced that assets/routines/stock were three disconnected systems. Answer was no; built the actual linkage:

- **Bug fix**: `state.js`'s `updateAsset`/`addAsset` now call a shared `computeNextServiceDue(asset)` (baselines from `lastServicedAt` if known, else today) whenever `serviceIntervalDays` changes — was a blind `Object.assign` before, so the card silently went stale.
- **suggestedRoutines on catalog assets**: ~45 of the 77 asset entries now carry a `suggestedRoutines` array (memo §4.2-shaped templates — title/trigger/effort/consequence/ownerClass, optional `requiresItemKeys`). Deliberately empty on entries with no real household chore (mobile phone, sofa, bookshelf, etc.) — memo's own "if it doesn't help tell you something before it becomes a problem, it doesn't belong" principle, applied to content curation this time. `assets.js`'s Add/Edit sheet shows these as pre-checked toggle chips (on catalog select when adding; via a "+ Add suggested routines" button when editing an existing catalog-linked asset) and creates the checked ones as real, `assetId`-linked routines on save — verified live, adding suggested routines to the mock Geyser created "Service geyser" and "Check pressure relief valve," both immediately visible on Today.
- **Naming-mismatch bug found while testing this**: the catalog's `"AST-GEYSER"` entry was named "Geyser (storage water heater)" while `mock-data/assets.js` and `packs/bath.json` both just say "Geyser" — `getOrCreate`'s exact-match lookup never found it, so the mock Geyser silently got a throwaway custom catalog entry with no icon/suggestedRoutines instead of the real one. Fixed by renaming the catalog entry to plain "Geyser" (also fixed "Boiler (central heating)" → "Boiler" preemptively, same risk). **Lesson: catalog entry `name` must exactly match whatever mock-data/pack JSON already uses, not just read well** — nothing type-checks this, only manual verification catches it (which is how this one was found — the "Add suggested routines" button was missing for the mock Geyser until the rename).
- **`js/roomTemplates.js`**: per-space-type suggestions for all 15 space types, generalizing the 5 onboarding packs so *any* space type gets a starting point, including ones no pack covers. `house.js`'s "Add space" flow follows a create-then-review pattern: space is created immediately, then (if the type has suggestions) a "Suggested for {name}" sheet opens — same confirm-don't-create chip-toggle pattern as onboarding, "Keep"/"Skip" per row. Verified live: adding a "study"-type "Home Office" correctly offered Desktop computer/Office chair/Printer/Printer paper/Ink cartridge/Dust desk routine; unchecking Office chair correctly excluded only that one from the 5 things created.
- **Round 3 (same session)**: user asked to (a) unify `roomTemplates.js` and `packs.json` rather than hand-duplicating the same content twice, (b) add robot vacuum to the catalog, (c) add pooja/entertainment/dining/garage/terrace space types with real content, (d) fix space-type chip labels showing raw `whole_home`-style keys with underscores.
  - **De-duplication**: `roomTemplates.js` was rewritten so pack-covered types (bath/bedroom/living/utility/entry/whole_home) now derive their suggestions **live** from `packs/*.json` — filtered by each pack entry's own `spaceType` field, resolved to catalog entries via `findExact`. Only the pack-uncovered types (balcony, study, storage, outside, plus the 5 new ones below) stay hand-authored in a much smaller `HAND_AUTHORED` map. `packs.js` gained a sync `getCachedPacks()` getter (returns `[]` before `loadPacks()` resolves); `boot.js` now fires `loadPacks()` at startup so it's warm by the time anyone opens "Add space." Verified live: a fresh "Guest Bathroom" (bath type) produced the exact same Geyser/Toothpaste/Toilet cleaner/.../Descale showerhead set as `bath.json` — confirming it's genuinely reading the pack, not a stale copy.
  - **New assets**: `AST-ROBOT-VACUUM` (own `robotVacuum` icon, distinct from the handheld `vacuum` icon) and `AST-GARAGE-DOOR-OPENER` (`garageDoorOpener` icon), each with suggestedRoutines.
  - **New space types**: pooja, entertainment, dining, garage, terrace — each with a new space icon (`pooja`/`entertainment`/`dining`/`garage`/`terrace` in `icons.js`) and a `HAND_AUTHORED` template (e.g. pooja → incense/candles + "Clean pooja room"/"Change flowers"; garage → car/garage-door-opener/lawn-mower + engine-oil/wiper-fluid + "Organize garage"). Also caught and fixed a **pre-existing gap** while auditing space-type coverage: `study`, `storage`, and `outside` had no space icons defined at all — `Icon()` was silently returning an empty string for their House rows. Added all three.
  - **Chip-label fix**: `house.js`'s `SPACE_TYPES` was a flat array of raw type strings (`"whole_home"`), so `chipGroup()` rendered the literal underscored key as the button label for every type, not just whole_home — just less noticeable on ones like `"bath"` that don't contain an underscore. Converted to `{value, label}` pairs with real display text for all 15 types. The underlying stored `type` value (e.g. `"whole_home"`) is unchanged — only what's shown to the user changed, so no data migration was needed.
- **Routines consume stock**: `requiresItemIds` (already in the memo's schema, previously unused) now has a UI — routine.js's builder gets a "Uses this stock (optional)" multi-select. `state.js`'s `completeOccurrence` decrements each linked item by 1 unit on completion (simplification — same amount regardless of unit type; not restored by the 5s undo, only the occurrence/ledger are). Verified live: completing "Deep clean bathroom" (mock-seeded with Toilet cleaner linked) dropped its qty from 2 to 1 and correctly reclassified it into the Low bucket.
- **Item consumption rate + early warning**: items carry `burnRate` (units/day, optional) and a new `lastRestockedAt` (set whenever qty increases — `adjustItemQty`, `updateItem`, `addItem` all touch it now). `stock.js` computes `projectedDaysLeft = qty / burnRate` and shows "~N days left" on every row; if that projection is ≤3 days, the item now lands in the Low bucket **even if the raw quantity hasn't crossed par level yet** — a light, honest precursor to memo §5.2's burn-rate learning (this is static, not EWMA-adapted; that's still genuinely Phase 5). Verified live against the mock household's existing `defaultBurnRate` values without needing to add any manually (Toothpaste ~83 days, Handwash refill ~10 days, Detergent ~15 days, etc., all showed correctly on first load).

## Known limitations to revisit, not bugs

- `items.status`/`projectedOutAt` are static mock values, not computed — real burn-rate learning (memo §5.2) is Phase 5.
- House Line's per-day effort weighting (`cosmetic 1 / degrading 1.5 / damaging 2.5 / safety 4`) is a placeholder scale for visual variety, not the memo's §5.5 load-balancing formula (that's Phase 5 too).
- No batching (§5.6), load smoothing (§5.7), or seasonal city map (§5.8) yet — seasonal routines just fire at raw month-window start.
- Long-press-to-reassign (memo §8.2) is not implemented — intentionally deferred rather than stubbed with a fake action.
- Deletes (space/item/asset/person/routine) use a native `confirm()` and are immediate/permanent — memo §4.4's 30-day soft-delete + "Recently removed" recovery isn't built (that's a Settings/More feature, later phase). `confirm()` satisfies §8.3's "no modal blocks anything except destructive confirmation" for now.
- `routine.js`'s condition trigger UI only supports "when this item runs out" (`op: eq, value: "out"`) — matches the only case `engine.js` needs today; extend both together if a pack needs a richer condition.
- `.tabbar` must stay nested **inside** `.app-body` in `index.html` — briefly wasn't, which silently broke the layout. No longer breakpoint-dependent since the sidebar was dropped (see locked decisions), but keep it nested regardless.
- Catalog entry `name` strings must exactly match mock-data/pack JSON names for the linkage to resolve (see the Geyser bug above) — nothing enforces this automatically. If a future pack or mock fixture references a catalog asset/item by name, double-check the exact string against `js/catalog.js` rather than assuming it'll match.
- Room templates (`js/roomTemplates.js`) don't cascade into each suggested asset's own `suggestedRoutines` — e.g. accepting "Desktop computer" from the Home Office template doesn't also offer its (currently empty, but could exist later) routine suggestions. Kept flat deliberately to avoid nested-suggestion complexity; if an asset's own routines matter, edit it afterward from Assets, which does offer them.
- Routine-consumes-item decrements are a flat 1 unit regardless of item unit (piece/ml/kg) and aren't restored by the 5s undo — only the occurrence/ledger snapshot is. Fine for "piece"-like consumables (toilet cleaner, detergent scoop), less meaningful for something like a 500ml handwash bottle.
- `roomTemplates.js`'s pack-derived suggestions depend on `loadPacks()` having resolved (`boot.js` fires it at startup, cached via `packs.js`'s `getCachedPacks()`). In practice this is near-instant for 5 small local JSON files, but if someone opened "Add space" in the first few milliseconds after page load, pack-covered types (bath/bedroom/living/utility/entry/whole_home) could show fewer suggestions than usual. Not defended against — low enough risk to leave as-is for now.
- Catalog custom entries (`js/catalog.js`'s `custom` array) live only for the tab's lifetime — reload and they're gone, so a freshly-typed "Shoe polish" won't survive a page refresh yet. Needs Firestore in Phase 4.
- After adding any new route file, **grep `boot.js` to confirm it's actually mounted** — `assets.js` sat fully built and completely unreachable for an entire phase before this was caught. Don't trust "the file exists and looks right" as done.
